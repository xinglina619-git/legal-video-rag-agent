# 简历与面试讲解手册

## 1. 项目一句话介绍

这是一个面向法律纠纷材料整理的多模态 RAG Agent。它支持通过问答采集案情，也能处理文档、图片、音频和视频材料，把不同来源统一成可追溯证据片段，再结合权威依据检索和人工复核，生成供法律咨询准备使用的初步分析报告。

## 2. 简历写法

可以写成：

> 法律多模态 RAG Agent：基于 FastAPI、Streamlit、LangGraph、Qdrant 构建法律纠纷材料分析 Demo，支持案情问答、文档/图片/音视频材料上传、权威依据检索、报告生成、人工复核与 PDF/Word 导出。

> 设计统一证据结构 EvidenceSegment，将 PDF 页码、图片 OCR、音视频转写时间戳统一纳入索引和引用体系；基于 Qdrant 实现 dense + sparse + RRF 混合检索，提高事实材料和法律依据召回稳定性。

> 针对法律场景加入隐私脱敏、来源引用、人工审核、免责声明和“不输出胜诉率/确定法律结论”等安全边界，降低大模型幻觉和误用风险。

## 3. 高频面试题

### Q1：这个项目和普通 RAG 问答有什么区别？

普通 RAG 往往是“上传文档后聊天”。这个项目是案件工作流：先采集案情，再上传多模态材料，再确认案情摘要，最后生成报告并人工复核。它不是只回答一个问题，而是围绕一个案件持续组织材料、检索证据、生成报告。

对应代码：

- `streamlit_app.py`
- `app/services/cases.py`
- `app/services/agent.py`

### Q2：为什么要设计 EvidenceSegment？

因为法律材料来自不同模态：PDF 有页码，视频有时间戳，图片需要 OCR，音频需要转写。如果不统一结构，后续检索、引用和导出都会变得复杂。EvidenceSegment 把这些材料统一成同一种可索引片段，同时保留来源信息。

对应代码：

- `app/services/normalizer.py`

### Q3：视频是怎么处理的？

视频先用 FFmpeg 提取音频，再用 faster-whisper 做语音转写；同时按固定间隔抽帧，用 RapidOCR 识别画面文字。最终音频转写和画面 OCR 都会变成 EvidenceSegment，并保留时间戳。

### Q4：RAG 检索怎么做？

项目使用 Qdrant，分别维护本案证据库和权威依据库。检索时同时使用 dense embedding 和 sparse embedding，再通过 RRF 融合结果。这样既能理解口语化描述，也能召回法律关键词和专有表达。

对应代码：

- `app/services/qdrant_store.py`

### Q5：怎么降低大模型幻觉？

主要有四层控制：

1. 提示词要求只能使用给定案情和权威依据；
2. 报告必须列出来源引用；
3. LangGraph 中设置人工复核节点；
4. 明确禁止输出胜诉概率和确定裁判结论。

对应代码：

- `app/services/agent.py`

### Q6：Agent 体现在哪里？

Agent 体现在 LangGraph 编排的多步骤工作流，而不是一次模型调用。流程包括证据检索、权威依据检索、报告草稿生成、人工复核中断和恢复。

### Q7：为什么法律项目要人工复核？

法律属于高风险场景，模型适合做材料整理和咨询准备，但不应该直接替代律师判断。人工复核可以检查事实、依据有效性和表达边界，降低误用风险。

### Q8：权威依据库为什么可能是 0？

权威依据库是单独维护的，不等于用户上传的案件材料。如果用户只上传了证据材料，没有导入法规、司法解释或官方案例，本地权威依据库数量就是 0。报告仍可生成，但缺少本地法条依据。

### Q9：为什么上传材料后要归一化并索引？

归一化是为了把不同文件格式转换成统一证据片段；索引是为了后续按问题检索相关片段，而不是每次把全部材料塞进模型上下文。这样更节省上下文，也能保留页码和时间戳引用。

### Q10：如果材料很多，会不会超过模型上下文？

不会直接把全部材料发给模型。系统先将材料切成 EvidenceSegment 并写入向量库，生成报告时只检索 top-k 相关片段。后续可继续增加摘要压缩、分层检索和重排机制。

### Q11：为什么不用直接把视频传给大模型？

直接传视频成本高、可控性差，也不利于引用回链。当前方案先把视频转成文本转写和画面 OCR，再统一进入检索链路，能保留时间戳，也能和其他材料一起检索。

### Q12：长视频或大文件处理很慢，如何避免 HTTP 超时？

材料上传和报告生成可以返回 `task_id`，由 Redis/RQ Worker 在后台执行。`task_records` 保存任务状态、阶段、进度、尝试次数和错误信息，前端通过 `/tasks/{task_id}` 查询。开发环境仍可切换回 `inline` 模式，避免 Demo 依赖 Redis。

### Q13：任务执行失败怎么办？用户重复点击怎么办？

任务在 `max_attempts` 内自动重试，最终失败时保留错误类型和最后错误信息。上传任务使用内容哈希生成幂等键，活动任务会被复用，不会因为用户重复点击而重复转写和索引。

### Q14：取消任务会不会直接杀掉 Whisper 或 FFmpeg？

不会强制终止底层进程，而是采用协作式取消。排队中的任务立即取消，正在运行的任务设置 `cancel_requested`，在当前阶段结束后不再进入下一阶段或下一次重试。这样可以避免产生半写入的索引数据。

### Q15：项目现在离生产系统还差什么？

主要差异在：

- 用户注册和多租户隔离；
- 权限控制；
- 更完整的死信队列和任务补偿；
- 操作日志；
- 对象存储；
- 检索效果评估体系；
- 更严格的法规有效性校验。

但是作为 Demo，当前重点是展示 AI 应用开发的完整链路，而不是做一个完整 SaaS。

### Q16：为什么还要引入 JEV？直接让 DeepSeek 输出 JSON 不行吗？

JEV 在这个项目里不是第二个报告生成模型，而是独立的决策层。DeepSeek 负责理解材料、检索上下文并生成报告；JEV 负责回答“证据是否足够”“是否存在越界表达”“是否必须人工复核”等边界清晰的问题，并返回概率和置信度。这样可以把模型的自由文本输出和流程控制分开，避免用字符串解析来决定是否放行高风险报告。

JEV 默认关闭，调用失败时回到人工复核；它不能批准报告，也不能输出胜诉或责任结论。质量门只发送脱敏后的报告和引用摘要，并记录固定模型版本、请求 ID 和置信度，方便后续做准确率、升级召回率和校准评估。

### Q17：JEV 能不能直接处理上传的视频？

不应该作为主链路。视频仍由 FFmpeg、Whisper 和 OCR 转成带时间戳的 EvidenceSegment，再由 RAG 和报告模型处理。JEV 只消费脱敏后的结构化文本状态，用于质量判断和流程分流；原始视频处理和报告生成仍由现有多模态管线负责。

## 4. 演示建议

建议使用民间借贷纠纷作为演示案例，因为它天然包含：

- 当事人叙述；
- 借款金额；
- 转账记录；
- 聊天催款；
- 还款争议；
- 借款合同或借条；
- 相关法律依据。

演示路径：

1. 创建“张某与李某民间借贷纠纷”；
2. 通过问答补齐金额、时间、还款情况；
3. 上传 demo 目录中的转账记录、聊天记录、案情摘要；
4. 确认案情；
5. 生成报告；
6. 展示报告中的证据引用、权威依据引用和 PDF/Word 导出。
